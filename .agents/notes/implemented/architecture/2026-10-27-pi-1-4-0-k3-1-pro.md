# Pi 1.4.0 and sealed Kimi K3.1 Pro catalog

Status: implemented
Date: 2026-10-27
Translation: pending

## Abstract

Molly now embeds Pi 1.4.0 and offers `kimi-coding/k3.1-pro` through the existing native Kimi connection and model picker. The approved design deliberately combined two reviewable layers in one branch: a build-time native catalog overlay and the engine upgrade. Pi 1.4.0 predates this model in its offline catalog, so a version bump alone was insufficient. The build refreshes only Kimi's native catalog through Pi, seals only `k3.1-pro`, and restores the same entry for the UI and every worker with runtime catalog networking disabled. No runtime catalog RPC, Settings refresh action, user-level cache or custom Kimi provider was added. Live acceptance covers the installed macOS arm64 Molly Preview: the native membership API key connection passed text, editable design, continuation, save/export and restart checks, while a separate OAuth connection passed text and post-restart read-only smoke checks. Independent human visual-quality sign-off and the remaining platform/account matrix stay open.

## Decisions

**Native overlay, not a second model definition.** The build uses `ModelRuntime.refresh({ providers: ['kimi-coding'] })` with an in-memory synthetic credential and `InMemoryModelsStore`. It retains only the native `k3.1-pro` model from the resulting `ModelsStoreEntry`, excluding highspeed, other additions and all remote overrides of existing models. Strict validation pins the default Kimi endpoint, OpenAI Chat Completions protocol, text/image input, 1M context, 131072 output tokens, `low/high/max`, and Kimi compatibility fields including `requiresReasoningContentOnAssistantMessages`. The model carries no credential or authorization header.

The build proves a JSON/offline round trip adds exactly one model while preserving every previous Kimi definition. A future SDK that already contains the target skips the refresh. Refresh failure may reuse only a checksum-valid previous overlay for the same engine; otherwise it fails rather than silently shipping without the target. Standard clean builds without a valid previous overlay therefore require a successful refresh when the SDK lacks the model.

**One sealed catalog for UI and execution.** `native-model-overlay.json` and the derived `model-catalog.json` enter the existing resource manifest and build ID. Workers and the packaging probe verify the overlay checksum and engine before credential grants or inference, then restore it with `allowModelNetwork: false`. The existing protected catalog publisher, connection `models` allowlists, default-endpoint behavior, native API-key/OAuth flows and ACP contracts remain unchanged. No model is selected implicitly and a missing/corrupt overlay fails closed.

**Pi 1.4.0 and scoped dependency compatibility.** The four Pi packages and `PI_ENGINE_VERSION` move from 1.3.0 to 1.4.0. The Google override now targets `@earendil-works/pi-ai@1.4.0>@google/genai: 2.23.0`; the staging assertion still requires 2.23.0. Electron's existing direct `ws` range moves to `^8.22.0` to satisfy `openai@7.19.0`'s optional peer; other CLI/Loro `ws` resolutions are not promoted. Third-party notices were regenerated. Pi and its add-ons remain unmodified published packages.

**History and known limits.** A synthetic v2 session was written through the public Pi 1.3.0 `SessionManager` before the upgrade and is resumed under 1.4.0 in tests. Existing v1 history coverage remains. The 1.4.0 retry classifier/backoff still lacks the deferred bare-529/ECONNRESET and Retry-After behavior, and its generic transient match does not resolve every wrapped permanent error; #143 is not declared complete.

## Reuse ladder

- Reused Pi's native online catalog, `ModelsStoreEntry`, in-memory store, provider/authentication and protocol compatibility instead of copying model metadata into a custom provider.
- Reused Molly's offline catalog projection, protected publisher, sealed manifest/build ID, worker configuration and credential grant instead of adding runtime catalog state or RPC.
- Reused the existing dependency closure, signature resealing and packaged synthetic smoke. No SDK patch, fork, global fetch replacement or transport workaround was introduced.
- Advanced OpenAI-compatible declaration was rejected for this native preset because it would not preserve Kimi OAuth and reasoning-history semantics by construction.

## Evidence

- Before the engine bump, the overlay layer built and passed all 413 then-existing/new harness tests on Pi 1.3.0. After the bump and the additional managed-ACP and genuine-history tests, `MOLLY_PLATFORM=local pnpm check` passed all workspace typechecks, lint, tests, i18n and import/platform/public-boundary guards: 415 harness tests, 3,018 CLI tests with three existing skips, 3,406 component tests, and the Electron test commands. The existing three Loro-streams skips remain.
- Native synthetic tests cover catalog refresh without an Authorization header, exactly-one-model sealing, no highspeed or existing-model override, offline restoration, checksum/engine/endpoint/protocol/credential-field rejection, verified-only fallback, native image/high-effort/tool/reasoning-history requests, and a managed ACP worker selecting `k3.1-pro/high`.
- `MOLLY_PLATFORM=local pnpm build` passed. The production orchestration test pins preservation before Vite's `emptyOutDir`; an additional standard build whose `pi.dev` request returned 404 reused a byte-identical verified overlay after Vite emptied `dist`. CLI and Electron staged manifest verification, worker probes and packaged Codemode/native-tool smoke passed on Pi 1.4.0. Both catalogs contain the four previous Kimi models plus only `k3.1-pro`.
- The first unpacked-package attempt passed the packaged Node 24.21.0 sealed-SDK/native-binding probes but stopped when Apple's codesign timestamp service was unavailable. Retrying the unchanged packaging/signature configuration succeeded. `codesign --verify --deep --strict` and verification of all 19,685 sealed resources then passed on the macOS arm64 app. The signed artifact was an unpacked app, not a DMG, notarization or publication; subsequent Molly Preview installation and restart supplied scoped installed-app evidence.
- Using the installed Preview's native Kimi Code membership API key connection with `k3.1-pro/high`, 20 real model requests completed: one text smoke, 15 design requests, three continuation requests and one post-restart read-only request. The run produced an editable 800×600 poster from a synthetic `#2563EB` image, native render/read-image results, a `read`/`edit`-only continuation that saved V2, restart persistence and an 800×600 PNG export. No paid image generation/edit call or modification of pre-existing works was made. These requests establish functional evidence, not independent human visual-quality approval.
- A separate Preview session selected the native Kimi Code OAuth connection, not the membership-key connection. Two real requests—initial text and post-restart read-only—completed with `stop` and zero tool calls. Run snapshots recorded `authType: openai_oauth`, `providerPresetId: kimi-coding`, `modelId: k3.1-pro`, `thinking: high`, OAuth metadata and completed native end entries. This is OAuth smoke/restart evidence only; token expiry, revocation and OAuth-driven design flows remain untested.
- `pnpm format` completed without unrelated file changes. An initial full-check run under context-mode's temporary path hit one stale-Unix-socket fixture ENOENT; the unmodified test passed 5/5 in an ordinary shell, and the subsequent complete check in that environment passed.

## Limits

Live evidence is limited to the macOS arm64 Preview scenarios above; it does not establish regional, subscription or other-account coverage. `k3.1-pro-highspeed` is intentionally absent. Paid image generation/editing, independent human visual-quality acceptance, OAuth token expiry/revocation, OAuth-driven design flows, DMG/notarization, clean-machine installation and Windows/Linux execution remain outside this acceptance. Existing `k3-256k/high` live evidence remains attached to that model and is not transferred to K3.1 Pro. The embedded-harness Spec remains `draft`; the implementation and user-approved direction do not constitute linked approval of a revised Spec revision.
