# 版本已写入后画布刷新失败的结果语义

Status: implemented
Translation: pending

## 摘要

“保存版本”先把当前设计写进本地 Git 历史，再同步原生画布。若第二步抛错，旧调用会把整个操作当作失败，用户可能在未看到版本号时重试并误判写入状态。现在主进程在写入成功后返回版本收据和独立的刷新错误；界面先刷新历史，再明确提示“已存为 Vn，但画布未能刷新”。隔离原生回归证明注入的写后脚本异常不会隐藏已持久化的版本；早前真实模型轮次的具体异常源头仍无法由旧日志确定。

## 问题与证据

[内置浏览器验收记录](../../proposed/architecture/2026-09-22-embedded-browser-account-import.zh.md) 中，一轮真实 Kimi 任务完成图片导入、有效设计与预览后，点击“保存版本”收到 Electron 的 `Script failed to execute`，界面没有显示版本。另一轮重做通过。旧记录没有保存失败瞬间的历史读数，所以不能断言那次究竟在 Git 写入前还是写入后失败。

`createDesignVersion` 的顺序为：画布 flush、`history-create`、再次读出、对保留的原生画布执行 `snapshot` / `rebase` 或同步刷新。旧实现让后半段任何异常向外冒泡，掩盖可能已经成功的 `history-create`。原生验证在 `history-create` 后强制让 `window.molly.snapshot()` 抛错，修复前得到通用 `Script failed to execute`，未返回版本；这个可复现路径与历史日志文案相同，但不证明历史故障由同一个脚本引起。

## 处理与取舍

保留现有 flush 与独占替换门禁。只有 `history-create` 返回版本后，才记录写入结果；之后的画布刷新失败被附到该版本收据上，状态广播仍通知界面。写入前失败继续抛错，不伪造版本。界面先重读历史和画布状态，再显示带版本号的刷新失败；正常路径仍显示成功提示。

另一种做法是刷新失败时回滚 Git 提交，但版本可能已被其他读取者观察，回滚还会引入新的持久化失败路径。直接把全部异常当保存失败也会让用户不知道版本是否已经存在。因此沿用设计服务已有的“持久化成功与画布重载分别报告”合同；不自动重复创建版本或静默重建画布。

## 验证与限制

隔离 Electron 原生验证先在旧实现下复现写后失败，修复后确认 `reloadError`、返回的提交 ID、当前版本基准和 `history-list` 最后一笔一致，其他版本分支/恢复断言亦通过。`pnpm check`、`pnpm e2e:check`、完整桌面 E2E（6 场景/37 步）及 `pnpm run docs check` 均通过。测试只注入了一类写后原生脚本故障；真实签名安装包中跨重启保存与原始间歇故障的具体来源仍需后续观察。
