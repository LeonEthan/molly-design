# Converge on a solo, local desktop product

Status: proposed
Translation: current

[简体中文](2026-09-15-local-only-product-scope.zh.md)

## Abstract

The public Molly Design desktop already uses local composition, while inherited product-cloud, remote-host, multi-user collaboration, and mobile-product implementations remain in public source and shared UI. This proposal narrows the maintained product to solo creation on one local desktop and removes entries, runtime paths, and code with no current product purpose. Local background execution, multi-window synchronization, file capabilities, and narrow desktop layout remain; explicitly chosen model services and trusted public downloads may still use the network. Deletion must follow real consumers and preserve reads of existing Molly Design data, because static scans and successful builds do not prove the end-to-end workflow survives.

## Goal and confirmed scope

This note records the confirmed product scope; the implementation plan remains proposed and entry-point convergence is underway. The [design platform Spec](../../../../specs/graphic-design-platform.zh.md) targets a solo local desktop and retains Agent and Bento creation while excluding cloud collaboration. The [independent-release Spec](../../../../specs/molly-design-independent-release.zh.md) does not add product cloud, accounts, mobile, or Web. The [README](../../../../README.md) states that the OSS desktop has no hosted workspace, team sharing, or remote product capability. This proposal goes further by removing inherited implementations that will not be maintained, beyond hiding user entries.

| Area          | Remove                                                                                                                                                        | Retain                                                                                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| remote        | Authenticated product cloud, cloud data transport, remote-host registration/connection/selection/execution, remote preview tunnels, and their background work | Electron-to-embedded-CLI IPC, local data transport and Agent execution; user-configured model/image services, public runtime downloads, and Molly Design app updates |
| collaboration | Multi-user sharing of artworks, sessions, or workspaces; invitations, member permissions, team visibility, and presence/publication for other members         | Multi-window synchronization on one machine, local session/artwork links, serial Agent/human editing, local file tree, edit conflicts, and diffs                     |
| mobile        | Mobile-product pages, native shell, gestures/bottom sheets, dedicated navigation, and stories                                                                 | Responsive layout and keyboard/pointer operation needed when a desktop window narrows                                                                                |

A local host is not a remote host: localhost previews and internal sockets are not removed solely because a name contains “remote” or “host.” A user’s own Git remote or external MCP/model service is not Molly Design product cloud. Design history remains in an independent local Git repository and needs no remote repository. Removing team sharing does not remove local CRDT durability, and removing the mobile product does not require a wide desktop window.

## Inspected implementation gap

- [CLI startup](../../../../apps/cli/src/commands/start.ts) composes both `createLocalCloudPort` and `createCloudCliPort`; [Fleet](../../../../apps/cli/src/lib/molly-fleet.ts) constructs a remote bridge when cloud tokens exist. The [local port](../../../../packages/platform/src/local.ts) has absent optional capabilities, showing local execution does not need those product-cloud services, but this does not prove every cloud branch can be deleted in one step.
- The [renderer root route](../../../../packages/components/src/routes/__root.tsx) uses static auth contexts on the local platform while retaining cloud composition. The [workspace runtime](../../../../packages/components/src/providers/create-workspace-runtime.ts) and [target router](../../../../packages/components/src/providers/workspace-target-router.ts) still support local/dual/cloud. Collapsing two planes must preserve local room routing, reconnect, and durable writes.
- The [settings catalog](../../../../packages/components/src/components/settings/settings-tabs.tsx) gates cloud entries, while the [sidebar](../../../../packages/components/src/components/loro-app-sidebar.tsx) still contains sharing and mobile branches. A gate may make an entry unreachable today, but it does not remove its implementation.
- The former mobile directory was shared by narrow Web and the desktop renderer. [Session detail](../../../../packages/components/src/components/sessions/session-detail.tsx) and routes contain mobile branches. Establish observable narrow-desktop behavior before deleting dedicated branches.
- [Code Collab v2](../../../../apps/cli/src/lib/code-collab/README.md) provides local file indexing, current changes, session diffs, and conflict handling. The [file-surface explanation](../../../../.agents/docs/sessions-file-surfaces.md) identifies desktop consumers. Deleting the directory by name would break local features.
- The [local Loro data-plane explanation](../../../../.agents/docs/cli-lib-local-loro-data-plane.md) describes multi-window and CLI-to-renderer room synchronization; the [design Spec](../../../../specs/graphic-design-platform.zh.md) still requires local Loro/Flock session and artwork links. “Remove collaboration” does not imply “remove all synchronization.”

These are source and documentation observations, not installed-package reachability proof or a complete consumer inventory. Decide the fate of `packages/cloud-api`, cloud-auth dependencies, and shared protocol fields only after checking imports, runtime construction, and historical reads in implementation slices. This note does not promise that a whole package or every field can be removed.

## Proposed implementation order

1. **Inventory reachability and baseline.** Trace product cloud, remote host, multi-user, and mobile entries from the local Electron build, embedded CLI, renderer routes/settings, and background tasks. Record observable local sessions, attachments, artworks, drafts, file previews, and narrow-window behavior. Distinguish source existence, construction, and installed-package reachability.
2. **Remove product entries and scheduling.** Remove remote-host selection/pairing, team sharing/invites/member pages, mobile-product navigation, and associated background work. Old deep links and explicit commands should reject clearly or route to a valid local entry without silently calling product cloud.
3. **Converge the runtime.** Remove concrete cloud-port composition, remote bridge, and cloud-room/reconnect logic module by module while retaining local identity, Loro/RPC, permission responses, Agent lifecycle, attachments, and previews. Delete cloud DTOs, dependencies, capability switches, and protocol writes once they lack consumers; keep necessary old-data read compatibility without writing new legacy feature records. Update the lockfile for package changes and run public-boundary checks.
4. **Remove mobile implementation and organize shared UI.** Delete mobile routes, dedicated components, and native behavior, leaving desktop layout that is actually needed at narrow supported widths. Keep desktop file, session, and canvas operations available.
5. **Update contracts and explanations.** Revise affected Specs, module READMEs, `.agents/docs/`, and nearest `AGENTS.md` for the final deletion. Any change to approved intent or guarantees returns the relevant Spec to draft for human approval of that revision; this note does not replace a Spec.

Make dependency-ordered, small deletion slices and ask whether complexity reappears in callers after each removal. If a module still serves several local consumers, retain it or isolate its present local responsibility. Do not add switches or empty adapters for a hypothetical cloud/mobile return.

## Trade-offs, risks, and acceptance

Hiding entries is smaller but keeps cloud/mobile paths in maintenance and does not meet the removal goal. Deleting all of Code Collab, Loro/Flock, or the embedded CLI may look more complete but removes local files, data flow, or Agent execution. This proposal deletes product-specific implementation and lets current local consumers determine which shared modules remain.

The material risks are loss of reads for existing Molly Design artworks, attachments, drafts, and session fields; accidental deletion of same-named remote/local RPCs; loss of local room health or permission responses when cloud paths are removed; and unusable narrow desktop windows after mobile layout deletion. Preserve installation and data isolation from Lody: do not scan, migrate, or delete Lody user data. Public runtime and app-update downloads remain governed by the [platform contract](../../../../packages/platform/AGENTS.md); removing cloud must not enable authenticated product-cloud requests or telemetry.

Acceptance uses the final local build and an isolated installed package: no product-cloud auth request, remote-host connection, or multi-user sharing entry; observable local design-session creation/recovery, Agent dispatch/cancel/permission responses, human edit/auto-save/save-version, attachment reads, previews, PNG/JPEG export, and multi-window protection; core operations work in a narrow desktop window; synthetic old Molly Design data reads while Lody data stays isolated. Tests use deterministic fixtures and explicit states, without public network or real sleeps. Run types, static checks, relevant tests, build, formatting, docs, and `check:public-boundary` for each implementation slice. A zero-keyword scan is not an acceptance signal.

**The golden case is a required final end-to-end acceptance case.** Reuse the frozen, executable [Kimi MagSafe replication case](../../../../e2e/KIMI-REPLICATION-ACCEPTANCE.md): the 285×2000 reference has SHA-256 `3f155040ce8152cd3e5808d000cbedb482307c1c1c1f4df68b6f50ae82baaa89`, the exact initial prompt is `复刻这个设计`, and the real Kimi Code CLI uses `K3` / `Thinking High`. The final Molly Design build after deletion must run a fresh isolated round through normal desktop attachment, Agent authoring, artifact commit, native Bento editing, auto-save/version, reopen, and PNG/JPEG export. Verify actual image delivery/read, artwork structure/assets/editability, and export readback. A human judges high visual consistency between this final output and the frozen reference; technical success or acceptance of an earlier round cannot substitute. Keep failed rounds, do not automatically rerun paid model work, and keep the live-model lane outside deterministic no-network regression. The [earlier single-file golden round](../../implemented/architecture/2026-09-15-single-canvas-authoring-redesign.zh.md#单文件黄金轮结果) passed technical, editing, and human visual review only for its then-current build, not for this deletion.
