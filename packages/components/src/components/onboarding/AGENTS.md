# Desktop Onboarding

- Electron opens `/onboarding` in the primary product renderer. Do not add a second window, renderer entry, provider tree, or runtime lease for onboarding.
- Bind the implicit local workspace into workspace-context atoms on `/onboarding` (same contract as `/$workspaceName`). Local builds skip the multi-workspace screen, and without that binding `RuntimeProvider` stays idle so the Connect-your-models step cannot see the flock-published built-in Molly catalog.
- The Electron main process owns the durable completion marker. Product navigation starts immediately alongside that write and never waits for its IPC; renderer storage owns only resumable phase state, and is cleared after both product navigation and the completion IPC succeed.
- Build the flow from platform capabilities. Local builds must not import or call cloud auth, workspace, or GitHub implementations.
- The local flow is ceremony → Connect your models → main canvas; there are no standalone folder or first-task steps. Persisted legacy phases (`projects`, `firstTask`, `summary`) and old selections remain stored history: they normalize to the Connect step and never revive or replace a retired selection.
- Connect your models is three rows — Language model and Image model (required) and Browser sign-ins (optional, never gates Finish). A connected row shows a check, a one-line summary and Change. Opening a row replaces `MollySetupArtwork` with that row's panel; below 1080px the panel overlays the column with Back. Panels reuse the encrypted Settings forms (`ModelConnectionSetting`, `ImageConnectionSetting`, `BrowserAccountImportPanel`) in their `panel` variant; the model panels stay mounted while closed so their readiness keeps reporting. An open panel pins its action row: the card does not scroll that row away, and editing or adding a connection keeps the form in a bounded flex slot so only the form body scrolls. An empty or short saved-connection list does not flex-grow, so it sizes to its rows and the first form starts at the top of the card; a longer idle list scrolls inside the card. The first-run form sizes to its content without `h-full` or `flex-1`, so short fields keep the action row directly below Advanced; tall fields still shrink and scroll above that row. Saved rows beside an open editor stay in a capped strip, and the editor keeps a 12rem floor while it fills the remaining height, with its action row pinned. Next completes onboarding only when both model rows report ready through the shared predicates in `lib/design-model-readiness.ts` (also used by Settings readiness and the landing send gate) and an eligible published built-in Molly exists on this machine. That Molly is auto-selected in the background; legacy/registry/custom targets and launch overrides are ineligible. Skip completes onboarding without model readiness. No CLI prefetch, installation, authentication or automatic setup is mounted.
- Onboarding borrows the existing presence-gated machine Flock catalog room, including the local daemon transport; a cold renderer replica is not the authoritative catalog. Keep its subscription through setup rather than disabling synchronization or synthesizing an Agent config.
- Catalog availability and saving credentials do not prove inference or choose a model. Skipping setup enters exploration; the landing blocks a design-session start while a model class is missing, names the missing class, and opens the Settings section that fixes it.
- User-facing onboarding copy calls the execution choice an Agent. Reserve Provider for Settings configuration management and internal `AgentConfig`/`ProviderSetup` state.
- Completion stays in the existing router and navigates to the created session when one exists. Reload recovery must target the normal product root after completion. Completing the Connect step binds first-session defaults — Agent = the auto-selected Molly, model = the connected LLM's offered model, thinking = product default — through `writeChatLandingDefaults`/`agentDefaultsCache`, so the landing composer needs no second pick. The default must be a projected model that the ready connection's current configuration offers (custom models, allowed `models`, packaged catalog), so a projection left over from a same-id edit is never saved; the catalog read and the image card's first read offer Retry on failure.
- Desktop onboarding owns the app theme for its whole route lifetime: enter and reload in `light`, and restore the persisted source to `system` only after completion succeeds or the route unmounts.
- `ceremony/intro-sequence.tsx` owns exactly three localized opening scenes at 0/3/6 seconds, holding the last until Start setup. Selecting any progress button stops automatic advancement for that visit; reduced-motion preferences disable automatic advancement and fades. The opening opts into Electron Tab traversal through `data-native-tab-surface`. Keep its Molly collage/poster/type direction in `intro-illustration-direction.md`, with skip and mute controls; later launches do not replay the opening.
- The bundled opening cue lasts nine seconds and never loops. A single foreground elapsed clock governs its position and each scene's remaining interval; Electron's native window foreground signal owns desktop pause/resume, with document visibility and window focus as the web fallback. Muting, blocked autoplay and manual scene selection do not reset elapsed time; only the sound control retries blocked playback. Leaving stops playback immediately. Do not persist opening state.
- Local setup independently uses the existing editorial artwork through `MollySetupArtwork`, never an index into the opening scenes or the coding-product tour. Cloud setup retains `TourStill` and its production Visual Annotation surfaces.
- The opening frame and local setup composition scale with both window width and height up to their caps, keep controls reachable at the 620 × 600 minimum, and switch to one centred column below 1080px.
- Workspace is required product context when the platform exposes multi-workspace onboarding, so it has no Skip or Enter Molly action. A failed workspace-list read keeps the investigation detail and a real platform-backed Retry action. Mutations use bounded waits: after a stale write the UI releases its attempt lock so the user may retry or go back, while late results never navigate or clear a newer attempt. A slow slug availability query is still pending, not failed: explain the slow network, keep Create disabled until the server answers, and let the user restart the check without treating elapsed time as validation. Query errors stay inside the slug field with their detail and Retry. A slug-less existing workspace is repaired inline because its Settings route is unreachable until the slug exists.
- Every onboarding error path writes its underlying error or failure detail to `console.error` even when the UI also shows an inline message or toast. Recoverable user actions must become retryable again after failure; never leave an error with only explanatory copy when the same operation can be attempted safely.
