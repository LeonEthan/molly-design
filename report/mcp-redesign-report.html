Research & design · not implemented · 2026-10-03

Rethinking MCP, image models and the browser in Molly's harness, aligned with Pi 1.0

Molly already runs Pi natively: Codemode on, native MCP and tool search, no second client, no paid retries. What still differs is how Molly presents its capabilities to Pi and how it models image generation. This report shows each area before and after, maps Pi primitives onto Molly components, and lists where Molly matches Pi's philosophy and where it diverges on purpose.

At a glance

Generic MCP

Catalog rows reach Pi without description or exposure, so every server, Molly's own included, gets Pi's default codemode exposure with a bare one-line listing.

Redesign: the catalog row becomes a lossless superset of a Pi mcpServers entry (description, exposure, toolExposure). Delete dead imageBinding.

Image models

Images are MCP tools on the built-in server, while Pi's own models.generateImages() is also live in every script and unmanaged.

Redesign: B1 uses a dedicated molly_image namespace with structured results and suppresses Pi's built-in image models. B2 makes it a Pi image provider once Codemode can pass per-call options.

Browser automation

One flattened seven-way molly_browser tool. By default every snapshot (up to 16 KB) or screenshot lands in context, and scripts can filter only by regex over untyped text.

Redesign: a molly_browser namespace of seven single-purpose tools with annotations and structured snapshots, so scripts filter before the model sees anything. Transport unchanged.

Pi 1.0 primitives that drive the redesign

Pi rejected MCP until it could be composed. 1.0 adopts it through Codemode: a QuickJS script calls tools and non-chat models, and only the script's output reaches the model. MCP servers default to being reachable only from scripts.

1 · Generic MCP connections

The catalog in the workspace Flock document stays Molly's single editable truth. The change is what that row carries into Pi.

changed / new pain point data flow

Changes

  • Forward the existing description, which closes G1. Pi renders the summary line for free.
  • Add exposure/toolExposure with Pi's exact names and semantics (G2). A GUI control replaces /mcp.
  • Accept a pasted mcpServers JSON entry. Secrets still go to the vault.
  • Delete imageBinding: readable until the next save, then dropped (G5).

Intentionally different

  • Catalog vs mcp.json: one GUI-editable, Flock-synced truth. No project files, so no project-trust question.
  • Vault + fd-3 vs mcp-auth.json OAuth: per-epoch profiles would lose sign-ins on worker rotation.
  • Fence kept (G4): any selected-row change retires the worker. This is the simplest correct credential boundary.
  • No annotation gate (G3): Molly keeps Pi's own no-prompt default, by owner decision. Settings shows hints so users can hide tools.

2 · Image model connections

Pi models image generation as an image model type run through models.generateImages(). In 1.0.0 that call takes only { input }, so it cannot carry background: "transparent", size or output_format, which layered design needs. The redesign therefore has two phases.

B1 changed B2 (when Codemode accepts options) unmanaged / removed path

Changes

  • B1: a dedicated molly_image namespace with a one-line description and instructions (billing and no-retry mechanics). Scene knowledge stays in the imagegen skill.
  • B1: one protocol-neutral schema (M3). outputSchema gives the parallel variant scripts that already work a typed result instead of JSON text (M5).
  • B1: close M1. The probe confirmed 57 OpenRouter image models reachable from scripts. The main session now uses Pi's public createCodemodeExtension({ models: false }). Limit: sub-agent children still build Pi's default Codemode, and no published setting changes that (upstream limitation, Q2).
  • B2: the image connection becomes a Pi image model. Usage flows into session cost (M2), errors become stopReason data, and the 900 s MCP timeout goes away (M6).

Intentionally different

  • Separate connection vs session credentials: the Spec requires the image service to be independent of the language connection, with no product default model.
  • Files, not ephemeral blocks: Pi doesn't save images. Bento needs validated, content-addressed media/ assets.
  • B2 is gated on upstream per-call options, including mask semantics. Model-ID variants (combinatorial) and prompt-parsed options (injection-prone) were rejected. B2 also needs a Spec revision to draft.

3 · Built-in browser automation

Pi ships no browser. Its idioms are small composable commands and MCP filtered through scripts. Molly keeps its visible, user-owned page and finite action set, and reshapes only the Agent surface.

Changes

  • Split the flat-kind tool into seven strict tools. This removes the union-erasure workaround (B1).
  • Hints per action: snapshot/screenshot are read-only; click/type are destructive and open-world.
  • Structured snapshot → { url, title, snapshot, truncated }, so scripts filter typed fields instead of regexing text (B2). This requires extending AgentBrowserReplySchema across the daemon/Electron reply, not just MCP registration.
  • Mechanics (refs, re-observe, never repeat an uncertain click) get one home in namespace instructions, ending the duplication between the tool description and the skill (B5).

Intentionally different

  • Visible GUI page vs scripts launching Chrome: the user's own session, takeover and password refusal. No arbitrary JS, CDP or cookie values.
  • Upstream Playwright catalog not exposed: it would bring browser_evaluate and roughly 14k tokens.
  • Transport kept (B3, B4): the owner-only socket and 500 ms poll are a desktop concern, not a Pi-alignment concern.

4 · Built-in server topology

Pi groups tools by server namespace, and each namespace gets one prompt line, its own exposure and its own instructions. Splitting Molly's single server lets each capability present itself independently, served by the same daemon HTTP host.

molly_render_preview becomes direct because the design loop is render → read PNG. A script cannot pass a file's pixels on, so routing through Codemode only adds a hop. This follows Pi's rule: direct for small, frequently used tool sets.

6 · Design-philosophy alignment

Pi's idioms (I1–I10, from pi-1.0-design.md §6) and where the redesign lands.

I1 · Default codemode, direct only when hotmatch

All built-ins default to codemode. Only molly_render_preview is direct, for the render → read loop.

I2 · One-line description, longer instructionsmatch

The catalog description is forwarded, and built-ins ship a description plus instructions. This also fixes skills that look for tools "in your tool list".

I3 · Compose and filter in scriptsmatch

Image variants fan out in one script. Browser snapshots are filtered before reaching the model.

I4 · Structured data for scriptsmatch

outputSchema on image and browser tools. The model still gets readable content.

I5 · Non-chat models as model typespartial

B1 is Pi-style presentation only. B2 waits until Codemode can carry background, size and format; Molly won't hack them in.

I6 · Backends are provider registrationsdeferred

B2 registers molly-image and reuses today's request builders. It needs a Spec revision.

I7 · Permission = extension over annotationsdiverge

Same no-prompt default as Pi. Molly does not add the optional gate (owner decision, 2026-09-30); hints are surfaced for user policy instead.

I8 · Never auto-retry tool callsmatch

Already true: paid image calls and uncertain browser actions are never replayed.

I9 · Cache-friendly, append-only contextmatch

Pi owns the mcp_servers section, and Molly adds no per-turn tool text. Lazy connect keeps first prompts fast.

I10 · Minimal, replaceable corematch

Deletes imageBinding, the flat-union schema workaround and the 900 s timeout on molly. No Pi patch, fork or second MCP client.

7 · Phasing, confirmations and open questions

Phase 1 · reductions no new capability

  • Forward catalog description.
  • Delete imageBinding (drop on save).
  • Remove Codemode's models global in the main session (Q1, Q2 settled).
  • Update skills: "listed in mcp_servers", not "in your tool list".

Phase 2 · presentation approved 2026-10-03

  • Catalog exposure/toolExposure + Settings control + mcp.json import.
  • Split the built-in server into molly, molly_image and molly_browser.
  • Browser: seven tools, annotations and structured snapshots. Image B1: neutral schema and structured results.

Phase 3 · B2 gated on upstream

  • When Codemode generateImages accepts per-call options: molly-image provider, save/open tools.
  • Spec returns to draft for the changed chain.
