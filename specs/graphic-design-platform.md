## Usage scenario

The user starts a design session, enters requirements and adds reference images, and uses a local Agent to generate an editable graphic design; they then refine it through element-targeted conversation or manual edits, and save, reopen and export images. The user finds past output through session history rather than managing a separate artwork directory. Normal creation requires no knowledge of Git repositories, branches, terminal commands or code review.

The core goal is to combine the mature Lody coding-agent workbench experience with Bento editable design capability, forming a design environment that Agents use autonomously (agent-naive) while reusing existing work paradigms. Agents read and write a YAML artwork projection, not PPTD.

Static single-canvas editing and rendering take the already migrated, validated Bento scope as the ceiling and only cut down from it; the necessary Lody integration adaptations and the explicitly confirmed automatic write-back, read-before-edit reminder hooks and live file preview are implemented within their own boundaries, without expanding the product on that basis. The Agent authoring surface is Molly's own YAML projection; PPTD and external PPT skills are not the live format contract, and there is no PPTD interop. The applicable first principles, reuse and Agent-autonomy rules are in the root [AGENTS.md](../AGENTS.md#design-principles-and-migration-scope).

This text incorporates the scope convergence confirmed on 2026-09-11: Agents resolve file conflicts themselves, the candidate workflow is removed, and the image tool supports both generation and editing with a user-required model. Implementation details and real integrations remained to be verified at that time. P0 fixed samples, P1 manual editing and the P2 Agent design loop have been implemented; phase evidence appears at the end and does not mean the newer goals were implemented or that the product passed release acceptance.

## Product scope

- A local single-user desktop workbench; each artwork has one static canvas, and a project can organize multiple artworks.
- Covers posters, covers, social images, banners, infographics, long images and general e-commerce images; scene knowledge lives in skills and reference materials.
- Keeps Molly's existing desktop architecture, UI design language, Agent integrations and local session capability; migrates in Bento's document, editing and rendering capability.
- The whole migration plan includes no standalone asset library, cross-artwork asset browsing or reuse, and does not defer one to later phases either. Image insertion, replacement and regeneration of a selected image on the current canvas, plus persistence of the assets the document needs, are retained; per-turn reference-image attachments are a separate requirement.
- The first release delivers PNG/JPEG. Multi-artboard, presentations, video, a template marketplace, cloud collaboration and other professional formats are outside this draft. The Agent authoring entry is one `design.yaml` plus local `media/`. Canvas dimensions, background, fonts and elements share that YAML, without a page manifest or separate page file. The first step retains Bento `id`/`kind` and structured text/table/chart; `.pptd` is not used, and no DSG or other new graphics model is invented.
- No generic per-turn result cards, per-turn history thumbnails, sidebar artwork thumbnails, or a dedicated candidate create/adopt/reject flow. Ordinary turn status, file diagnostics and the current-artwork entry reuse session capability; conflicts retain drafts for the Agent to continue. The Agent's render-preview and image-reading capabilities are retained.
- Attachment picking, paste/drag-drop, generic image/file preview, search/pin/rename, commands/shortcuts and session restore reuse existing Lody capability rather than being rebuilt. Reference-image integration only fills the gap between Molly's local combination and design input; generic attachment rendering is not part of the retired design result-card chain.

The home page keeps the original top bar and chat input structure. Size selection sits on the same row as the project directory, at the far right, right-aligned with the input box; it is not stacked on its own row, and there is no separate new-design button or name input. Size defaults to Auto with no required width/height; the fields appear and are validated only after switching to custom. Artwork creation and the durable first-turn input use the same submitted dimensions, explicitly asking the Agent to design at that width and height. Auto adds no fixed-size instruction; later user requests may change the dimensions. Pressing Enter with content reuses the existing Session submit and auto-naming flow and initializes a blank single-canvas artwork; Auto uses a default initial canvas in P1, adjustable later through the Agent authoring path, and Agent-computed sizing from content is not promised. A failed creation keeps the input draft.

## Responsibilities and persistence

The first-stage single-file contract has `format: molly-canvas/1`, required `size`/`elements`, and optional `background`/`customFonts`/`diagnostics`/`title`. Elements retain existing `id`/`kind`/`bounds`, without type blocks. Entry defaults, file metadata versus canonical state, explicit old-YAML conversion and test gates are defined in the [first-stage review plan](../.agents/notes/implemented/architecture/2026-09-15-single-canvas-authoring-redesign.zh.md#第一阶段审核方案). This concrete plan passed the current review.

The current artwork holds the latest working state, and the design session records the discussion and execution; by default one artwork maps to one main session in the first release. The user keeps historical nodes through "Save as version"; Git is the only history store, with no separate file-snapshot library or authoritative version index; autosave and ordinary Agent turns do not create a history version each time. Session archiving and deletion keep the original project's semantics, with no new behavior that deletes ordinary workspace files or design history; deleting a session record does not delete design files. Existing Git worktree cleanup rules do not gain authorization to delete the version store.

The existing CLI backend continues to own the Agent lifecycle, permission responses, sessions and turns. The design service owns format conversion, structural validation, asset registration, version checks and current-artwork saving; on conflict it preserves the authoring files and returns an actionable diagnostic. Electron owns desktop resources, the trusted editor bridge, the renderer process and native file interaction. The design service does not build a second Agent scheduler, diff-merge or chat store.

BentoDoc is the single authoritative state (canonical) of the current artwork. The artwork projection is an on-demand YAML file representation (one `design.yaml` plus local `media/`) for the Agent to read; the Agent authoring draft is the same layout the Agent is editing, validated before being committed as BentoDoc. The artwork projection and the Agent's authoring draft serve different purposes and are not two independently committable authoritative artworks. `design.json` and PPTD are not Agent authoring entries. Preview and export images are derived artifacts. The existing Loro/Flock stores sessions and artwork associations, and the local workspace stores the current artwork and assets; the two are not turned into duplicate, separately editable artworks.

Session and artifact identities are the basis of association; the baseline identifier of concurrent current-artwork saves detects state changes and is separate from Git history commit IDs. A failed write or notification of session metadata must not undo a persisted artwork; reopening recovers from the persisted association, with the exact commit and repair mechanism decided in technical slices. The user should not regenerate the same artwork because a notification arrived late.

## Editing and Agent turns

P1 supports a single canvas of 1–4096 pixels in each dimension. Any canvas-resize implementation must keep element positions and sizes; if an element would fall outside the canvas after resizing, the resize is rejected with the blocking elements named, without automatic scaling or cropping. As of 2026-09-16, the manual canvas-size entry in the editor (the page-setup panel) is retired with the Lovart-style canvas UI; canvas size is created and adjusted through the Agent authoring path (see the [canvas Lovart UI note](../.agents/notes/implemented/feature/2026-09-15-canvas-lovart-ui.zh.md), Chinese).

1. The same artwork is edited serially: before dispatch, new manual edits are blocked, the generic flush and pending saves complete, and only after success are the current-artwork baseline, selection, reference materials and skills frozen, then the Agent starts. If saving or launching fails, the input/edits are preserved and editing resumes once no turn is confirmed running.
2. Model, permission and tool capabilities are determined by the current Agent's real capabilities; support status is never fabricated, the Agent is never switched silently, and permission requests are never answered on the user's behalf.
3. After the Agent finishes naturally, artifacts are collected and validated; a file's appearance does not mean completion, and a successful Agent turn does not mean a valid artwork was committed. In a successful turn, an old authoring file that is provably unchanged and has no valid explicit resubmission this turn records no_artifact, and is not promoted or committed merely because it differs from the current canvas. The entry must be `design.yaml`; a leftover `.pptd` is not a valid artifact. Files and historical receipts are preserved; the explicit-resubmission boundary is in the next section.
4. While the Agent runs and while its artifacts are collected/committed, every Bento instance of that artwork is read-only to human edits; other artworks are unaffected. The app uses the existing execution state to drive its generic read-only capability and enforces the same check at manual change/save entries, not just by disabling buttons. The final commit still checks the baseline atomically; abnormal external changes or stale requests raise errors and preserve drafts rather than overwriting newer work.
5. Ordinary edits and regeneration share one commit flow: when the artifact is valid and the version check passes, the current artwork is saved — without classifying by prompt and without an extra adoption wait. Conflicts are left to the Agent, which re-reads, compares and edits files; the app provides no dedicated candidate approval or design-semantic merge.
6. Failures, cancellations, validation failures and uncommitted results are reported honestly, with execution status reusing the existing session display; ordinary discussion or a turn with no design output requires no extra result prompt. After termination, working files and the original artwork are preserved; when the user explicitly continues, the Agent reads the latest artwork and handles the draft; restarts or commit failures never trigger a model call automatically. Persistent commit receipts and historical facts are not deleted when UI is retired; existing candidate content stays readable as ordinary files for the Agent to process, and no new candidate workflow is added.
7. Element references carry the artwork, the current-artwork baseline and a stable element ID; when a selection goes stale the user is told explicitly, and no other element is guessed as the target. In the first release, references to the current artwork continue editing after a turn completes; referencing a live temporary preview mid-run is not expanded.
8. Read-only covers waiting for tools/permissions, cancellation in progress, and post-turn collection/commit; on normal completion, failure or cancellation, editing resumes only after execution and result processing are confirmed finished. With no valid artifact the original artwork is preserved. Closing a tab or disconnecting the UI does not unlock; reopening first checks the real execution state, and if the state is unknown the artwork stays read-only with recovery status shown. A late end event must not unlock a later turn, and overlapping dispatches of the same artwork keep the existing queue/reject mechanism.

On 2026-09-12 the user confirmed that Grok's "Stop" uses full-close semantics: terminate the current session's execution together with its background tasks and subtasks, while preserving the session record, current artwork and working files. The app confirms execution has ended through the public session-close capability and waits for artifact processing to finish before restoring canvas editing; a close failure must not be treated as stopped. The session continues along the existing resume path only when the user sends the next message, without automatically restarting or resending the stopped turn. This semantic fix has been implemented and verified (see the "Basis and verification status" section); a native cancel receipt is not evidence that the underlying request closed.

## Current-artwork reading and file consistency (P3 goal)

The 2026-09-12 revised goal is automatic write-back plus read reminders; the earlier read-sync/generation-proof implementation was to be converged afterwards, and old acceptance must not be treated as this revision already implemented.

- Bento keeps independent editing/rendering with generic change, snapshot/flush and read-only capabilities. Human edits automatically update the BentoDoc, the same-version YAML artwork projection and assets through Molly's design-save adaptation; Bento is unaware of the Agent lifecycle and does not wait for the Agent to sync.
- Reuse the existing autosave, reverse conversion and projection publication. Consecutive edits may be coalesced, and flush waits for the file result of the last completed edit; launching an Agent only waits for the existing save queue and files to be ready, never triggering a design sync first. Current-artwork entries such as create and restore share the same readiness condition.
- If the current artwork is saved but artwork-projection publication fails, the human result is preserved, clearly reported, and starting creation from a stale projection is blocked; reopening checks/rebuilds against the current-artwork version. Renaming files one by one or debouncing does not imply cross-file atomicity, and an old task must not overwrite a newer version.
- The BentoDoc → YAML artwork projection → BentoDoc roundtrip preserves the editing semantics exposed in the first release: stable element IDs, hierarchy, styles and asset references. Single-file authoring initially retains `id`/`kind` and Bento structured text/table/chart. Further type-block restructuring requires complete roundtrip and Agent operability validation and explicit approval of its concrete field contract. The projection does not use PPTD `elementId`/`elementType`, HTML rich text, theme `$ref` or `seriesDefaults`. Minimal format and bidirectional adaptation is done for grouping, multi-layer shadows and the like; nothing is silently dropped or rasterized. Restoring YAML layout, comments or aliases is not required.
- Keep the read-before-edit reminder loaded through public hooks/extensions: read the current contents before modifying an existing file; read the complete contents before replacing a whole file; re-read and adjust after a change/conflict; creating a new file does not require reading a nonexistent target. When continuing an artwork, the Agent should also read the latest current artwork rather than editing a retained draft from memory alone. Reuse the existing protections of native file tools without modifying the runtime.
- A reminder is a behavioral requirement, not proof of execution. A PreToolUse hook that only adds context does not guarantee that already-generated write parameters wait for a Read; record actual events, context delivery and native rejection semantics, and do not claim enforced read-first on every path of all five Agents. A static skill cannot impersonate a wired hook. No unified read ledger or per-generation proof is added.
- The current-artwork projection and the Agent draft are separate; autosave, reading and recovery neither overwrite an unfinished draft nor silently rebase its commit baseline. The app's projection is not collected as a new artifact, and previews are never saved back, preventing loops.
- Version conflicts are fed back through ordinary tool errors for the Agent to re-read, compare and adjust; an explicit resubmission still ties the exact draft to the expected current-artwork version. Merely re-reading or the presence of an old file is not promoted to this turn's artifact. A conflict discovered only after the turn ends preserves the draft/diagnostic and waits for explicit continuation, with no automatic restart.
- The formal commit independently validates structure, assets, provenance and the current-artwork version, protecting unsaved edits. Removing the old generation read-proof dependency also adjusts final collection; a missing reminder event does not by itself invalidate a valid artifact, and reminder delivery is not commit authorization. The five integrations are verified by actual versions, launch methods and tool paths, with no promise of global Shell/MCP interception.

Design guidance and optional helper tools live in skills; the app only does structural validation and observable outcome classification, without mandating tool-call counts, visual self-review rounds or a fixed completion flow. A missing tool does not imply a missing built-in Agent capability. Formal export continues to use the fixed Bento rendering path.

An Agent may render the YAML artwork projection through the existing `molly_render_preview`, then view it with an actually available image-reading tool and keep editing. The app does not require fetching images through result cards, nor equate render success with the model having read the image; when the preview tool is absent, the app only states the capability is unavailable and does not declare all visual review failed on the Agent's behalf. An optional finalize script is not a mandatory write order or a file-publish transaction.

## Built-in image tools

Molly's built-in MCP offers generate and edit, reusing the existing image connection, session permissions, transport and workspace asset saving. The user configures the URL, Key and required model; the product sets no default model, guesses no aliases and switches nothing silently. Existing user configurations keep their explicitly saved values, and an empty model is no longer auto-filled.

- Generate takes a prompt and produces an image; edit takes a prompt plus one or more source/reference images, with an optional mask. The default integration protocol is OpenAI Images-compatible generations/edits, and not every provider is required to support every parameter; when a parameter is unsupported the error is reported honestly, without silently falling back to text-to-image or repeating paid calls.
- Tool results are saved as workspace assets, and the Agent decides how to use them in the artwork projection; calling generate/edit itself neither commits nor replaces the current artwork. Bento's existing crop, replace and ordinary selection actions are reused, with no separate image-job system or mask editor.
- Attachment input, Agent image viewing and Bento manual image operations are independent of the image service and are not disabled when image MCP is unconfigured. Whether each of the five Agents can obtain actual image input is verified separately.

## One canvas and live construction

The right panel exposes one canvas with no Artwork / Preview source switch. While idle it displays and edits the active working artwork derived from the selected version; during Agent execution it displays this turn's latest valid read-only construction state in place. Actual file changes trigger bounded snapshot collection, structural validation and YAML → BentoDoc conversion; tool events only supplement this, without separate mechanisms for the five Agents. This pipeline does not schedule or complete Agents. External files and retained drafts do not replace the idle working artwork or have a separate preview entry.

- Subscriptions exist only for visible canvases that need live construction; consumers of the same workspace/entry share watching and conversion until the last consumer leaves or disconnects. Historical workspaces without consumers are not watched or continuously converted; background turns retain formal artifact collection.
- Watch `design.yaml` and the necessary asset directories; to catch first creation, rename replacement and missing dependencies, the nearest valid parent directory may be watched non-recursively with filtering. Targets adjust as dependencies change, without recursively watching the whole workspace. After subscribing, the initial files are checked; reopening, reconnection and the end of a turn with consumers actively re-check, compensating for missed notifications. A leftover `.pptd` is not an authoring entry.
- Consecutive events are coalesced, and repeat conversions are skipped by dependency set and file bytes; bounded wait and re-sample policies avoid indefinite waiting or busy retry under continuous writes. The document and asset bytes of one observation are frozen and re-checked for stability before conversion; debounce, per-file reads or structural validity are not treated as the author having finished a multi-file transaction. A valid intermediate draft may be previewed, but that is not proof the artifact is complete.
- Conversion/rendering is scheduled coalesced per project, and results bind the source digest, artwork and subscription generation; an older task must not overwrite a newer result or update a view that has switched. On invalid intermediate states, temporarily missing assets or unstable reads, the last valid preview is kept and the failure is reported; the editable current artwork is never cleared and the turn is never failed on this basis. A watch failure is reported as automatic preview updates being unavailable; formal collection is unaffected.
- Keep the current artwork visible during dispatch and before the first valid change, or the existing blank canvas for a new artwork; never present a previous turn's draft as new progress. Display tasks bind artwork, editing context, turn and source identity, reconciled on reconnect or opening mid-turn; stale tasks cannot replace new targets. Viewing, zooming and panning remain available during execution/processing, while editing, element references, export, saving versions and switching versions are disabled. The history list may open without changing the editing target.
- After the new rendering, assets, and actual container layout are ready, fit and center the complete canvas before replacing the image in place. Fit initial loads, valid live updates, completion reloads, version switches, and container-size changes. Retained unchanged views preserve manual zoom across hide/show; selection changes, ordinary manual edits, and invalid intermediate drafts do not reset it. Live granularity is valid files written to disk, not tokens or every write. Partial writes and missing assets retain the last valid image with a brief waiting state and inspectable diagnostics, without clearing the canvas or silently repairing content.
- Final collection, validation and commit remain independent. Editing resumes after successful commit and canvas readiness, without adoption confirmation. Failure/cancellation/no commit displays the latest confirmed current artwork and preserves working files; ordinary no_artifact is not an error. Prior preview success cannot commit content. Report saved-but-projection/canvas-not-ready separately and block stale editing/dispatch without restarting the Agent.
- Preview does not advance the current-artwork version, change the Agent draft baseline, or trigger saving or completion. App-produced artwork projections, formal storage, preview caches and export files are not watched as authoring entries or collected as new Agent artifacts, avoiding sync loops; provenance is never inferred by "ignoring the next event". The preview is read-only and updates automatically, with no manual refresh or import-into-current-artwork action; no artwork-directory import product is added, and there is no legacy `.pptd` import.

## Save, recovery and export

- Autosave, switching artworks, closing a tab and quitting the app share one save-confirmation semantic. Failures must be visible and must never be reported as saved; runtime state and artwork-saving state are each reported truthfully.
- If saving fails when switching artworks, closing a tab or quitting, the action is blocked and unsaved edits are preserved; the user may retry or explicitly discard, and drafts are never silently lost.
- Manual saves still check the version; when an abnormal multi-window/external edit stales the baseline, the overwrite is rejected and local content preserved. Serial editing removes the normal human-machine concurrency case, which does not prove all conflicts are gone; Agent file conflicts continue through tool feedback and session continuation.
- The implemented conflict save-as stays for now as a draft-preserving escape for abnormal cases and is no longer expanded as an everyday collaboration feature. Before removing it entirely, a draft-preserving exit for non-Agent concurrent edits must be explicit; the check cannot be replaced by a read-only button. Save-as still copies only the artwork and required assets, not session records; failure preserves the edits.
- After a crash or power loss, the last successfully saved artwork and assets are restored; edits still pending or mid-save may be lost. P1 does not promise crash recovery of drafts with no confirmed save, while normal leave actions still run save protection.
- History versions use the Git store of the next section; the neighboring project's full revision library is not migrated in, and no parallel snapshot backend is built. Editor undo/redo is separate from the history nodes saved by the human.
- While an artwork tab stays open, ordinary artwork/panel switching keeps undo/redo. Switching historical versions rebuilds undo and selection rather than undoing across versions. Closing the tab or restarting drops undo history without affecting saved artwork.
- Formal export is based on the saved current artwork, using the fixed editor rendering path, fonts and assets. Pending unsaved edits are handled before export; an old draft is never silently exported.
- PNG keeps transparency; JPEG fills transparent areas white. Pixel dimensions follow the actual canvas size; zoom only affects the interface display.
- Invalid documents, missing assets, fonts or render failures must raise errors; placeholders or window screenshots must not impersonate a successful export.
- The first release provides no artwork-directory management and no import of the neighboring project's artwork directory; old program data is left as is.

## Design versions

- The canvas top-right offers a separate Save version button and the existing history button. Autosave maintains one active working artwork. Save version first waits for completed edits to persist, captures consistent document/assets/fonts, and displays the new base after saving and binding it. Stable V1/V2 numbering and timestamps require no name; unchanged content against an existing base creates no duplicate node. Save as new artwork remains a separate operation.
- A history item directly switches the editing base, without a read-only viewing or Edit from here step. Flush all instances first; if current content has no history snapshot, preserve a selectable pre-switch version in the same Git backend. Protection failure blocks switching. Selecting the current base also restores its original content after protecting changes; identical content and base are a no-op.
- Saved versions are immutable, while the working artwork remains editable. Show V1 when unchanged, Based on V1 · New changes when modified, or Current artwork before a first base exists. Human and Agent edits remain serial on the same working artwork; dispatch reads the latest human edits, not only the base snapshot. Saving V4 from V1 records V1 as its source and preserves V2/V3. No named branches, separate working drafts per branch, merges or dedicated thumbnails are introduced.
- Git append order and design ancestry are separate. Versions and ancestry come from the same Git backend, without another authoritative index; unknown ancestry of old versions is not guessed. Persist the active base atomically with the current-artwork envelope, outside BentoDoc/YAML, and restore base/work on restart. Publish history before binding the base, report partial success, and make retries neither duplicate nodes nor overwrite later edits.
- Switching validates structure/assets and atomically checks the editing context, affecting only the owned artwork. Update the current Agent-readable projection while preserving drafts, receipts, conversation and unrelated files, without rebasing old drafts. All instances synchronize context, undo and selection. Report load/projection failure separately from persistence; stale content cannot be edited or dispatched while unready.
- Saving and switching versions are forbidden during preparation, execution and artifact processing. The history list may open, but there is no separate viewing target. Stopping still waits for actual execution and processing to settle. Enforce the artwork mutation check across windows and delayed requests, not only buttons; switching never automatically stops, restarts or calls an Agent.
- Git only stores historical content; current-artwork autosave, artwork-projection conversion, complete-file publication, conflict checks and draft protection remain the design service's job. A Git commit cannot prove that multi-file input came from the same edit version. Necessary temporary files do not act as a second persistent history store.
- Git history is a local capability, requiring no GitHub, remote repository, push or extra Agent turns. Molly manages an independent local Git repository, supporting creation in ordinary non-Git projects while isolating the user's branches, staging area and unrelated content; artwork restore must not be implemented directly with project-level reset/checkout.

## Workbench and boundaries

Keep the sidebar, tabs and chat input structure; by default the conversation sits beside a larger canvas, with a focused-canvas mode. Layers and properties expand on demand, image actions follow the current canvas selection, and switching views in a narrow window preserves edit state. Slides, presentations and other unsupported editor entries are removed.

Selected elements show a nearby floating property toolbar with existing typed controls and reference/image/style actions. Controls retain their screen size through artwork zoom, and toolbar/popups avoid viewport edges. Hide during dragging and reposition on release; empty selections, read-only states and live derived images show no editable toolbar. A ready working artwork selected from history supports the ordinary toolbar. This does not extend the single-canvas scope. Acceptance requires real Electron screenshots of all seven element kinds in both themes and per-image visual assessment separate from automated results.

Layout, settings, commands and onboarding follow the existing framework; P1 already has the focused-canvas entry — later verify its connection with preview/read-only rather than redoing it; Lody's current Zen hides the right panel and cannot directly substitute. Reuse the existing Agent guidance and local capability trimming, only changing code-task examples to design, with no new mandatory configuration pages. The image connection was wired in P2, with entry cleanup later; no save settings are added without a concrete need.

Git branch operations, PR/CI and other developer features leave the design main flow, and their no-longer-needed background work stops; design version history is Git's new consumer, keeping its necessary base capabilities without reusing the flow that auto-prompts the Agent to commit/push. Shared infrastructure is deleted only after confirming it has no consumers. Terminal, reference web browsing and session forking are decided per actual consumer; generic file, process, tool, diagnostics, permission and recovery capabilities continue to be reused. The new app identity and data directory must be isolated from the existing Lody and neighboring programs.

Follow the [platform boundary](../packages/platform/AGENTS.md) and the [shared protocol contracts](../packages/shared/AGENTS.md): no authenticated product-cloud requests or telemetry. The user-chosen Agent and image service may still reach external models — local-first does not mean offline generation; credentials never enter artworks, Roles or logs. Without an Agent or image service, existing artworks can still be edited, saved and exported.
